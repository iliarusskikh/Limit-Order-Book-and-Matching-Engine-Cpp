Orders

02 — Order Types & Time-in-Force

Orders as messages

An order is a request to change book state, not a trade. Trades are outputs of matching.

Minimum fields (conceptual):

Field Role
Identity order_id (unique while live)
Side Buy / Sell
Type Limit / Market (v1)
Quantity Remaining qty mutates on fills
Price Limit price; meaningless for pure market
Arrival Time or sequence for FIFO

Limit orders

Definition: buy (sell) only at price ≤ (≥) the limit, or better.

Behaviour:

  1. If not marketable (buy limit < best ask, or no asks): rest on the book at that price.
  2. If marketable (buy limit ≥ best ask): aggress — match immediately against opposite side, walking prices as needed, until qty done or no more eligible liquidity.
  3. Any unfilled remainder of a limit rests at the limit price (unless TIF says otherwise).

“Better” for a buy means lower ask prices first; for a sell, higher bid prices first.

Marketability test (limit)

Buy  limit is marketable iff asks non-empty AND limit_price >= best_ask
Sell limit is marketable iff bids non-empty AND limit_price <= best_bid

Market orders

Definition: take liquidity now at whatever prices the book offers; no resting price.

Behaviour in our v1 (document this; venues differ):

  1. Match against opposite side from best price outward.
  2. If book runs out before qty filled → cancel residual (do not leave a naked market order on the book).
  3. Emit an explicit residual-cancelled (or equivalent) event so tests can assert accounting.

Alternative policies you might hear:

Policy Meaning Our v1
Cancel residual Unfilled die Yes
Convert to limit at last trade / peg Rest remainder No
Reject if cannot fully fill FOK-like No (that’s FOK)

Time-in-force (TIF) — know the dictionary

We do not implement named TIFs in v1, but Useful vocabulary beyond v1:

TIF Behaviour
DAY / GTC Rest until filled, cancelled, or session end (GTC across sessions)
IOC (Immediate-or-Cancel) Match now; cancel any unfilled remainder — never rest
FOK (Fill-or-Kill) Fill entire qty now or reject with no partials
GTD Good till date/time
ATO / ATC Auction-only (open/close)

Mapping to v1:

  • Limit + rest remainder ≈ GTC/DAY without session end.
  • Market + cancel residual ≈ IOC market.
  • True FOK = extra pre-check: enough opposite liquidity at acceptable prices before any fill.

“IOC is a TIF; market is a type. A limit IOC is common: take what you can up to limit, cancel rest.”

Special / advanced types (do not build; name fluently)

Type Idea
Stop / stop-limit Becomes market/limit when trigger trades
Iceberg / reserve Display qty << total; replenish
Pegged Price floats with NBBO/mid
Midpoint / dark Non-displayed, mid execution
Post-only Reject if it would take; maker-only
Reduce-only Derivatives: only shrink position

Side conventions

  • Buy / Bid: willing to purchase; rests on bid book.
  • Sell / Ask / Offer: willing to sell; rests on ask book.

Aggressive buy hits asks; aggressive sell hits bids.

Quantity semantics

  • Incoming qty must be > 0.
  • On each trade of size q, both maker remaining and taker remaining decrease by q.
  • When remaining hits 0, order is fully filled and removed (no cancel event required beyond trades — optional “Filled” event is nice-to-have, not required).

Partial fill: trade qty < order remaining before the trade.

Cancel

  • Full cancel (v1): remove remaining qty of a resting order by id.
  • Cancel of unknown id / already gone → reject (book unchanged).
  • Cancel during matching of another order doesn’t apply — single-threaded sequential messages.

Amend / replace (out of scope): change price or qty. Real venues often implement as atomic cancel+replace with queue-priority rules (lose time priority if price changes; sometimes keep if qty down only). v1 users: cancel + new.

Self-trade

When the same logical owner would be both maker and taker:

Policy Behaviour
Allow Match as normal (our v1)
Cancel newest Kill aggressor (or resting) per STP mode
Cancel oldest Prefer keeping new liquidity
Decrement / adjust More exotic

Allowing self-trades keeps tests simple; mention STP as a one-line future flag.

Rejects (validation layer)

Typical reject reasons to support in v1:

  • qty <= 0
  • duplicate order_id
  • cancel unknown id
  • (optional) invalid price for limit (e.g. non-positive if you forbid it)
  • (optional) market order with non-zero price ignored or rejected — pick one, document

Rejects must leave the book unchanged.
