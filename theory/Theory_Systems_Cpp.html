07 — Systems C++ for Matching Engines

Language standard

Recommendation for this portfolio: C++17.

Reasons:

  • enum class, structured bindings, std::optional for BBO, string_view for scenario parsing.
  • Still widely expected in quant shop codebases.
  • This project locks C++17 in CMake (CXX_STANDARD 17) and does not mix standards.

Hot path rules of thumb

Match path should avoid:

  1. double / float prices — use int64_t ticks.
  2. Heap allocs per trade event if avoidable — vector<Event> reuse via clear() + reserve, or output iterator. v1 may allocate; know it’s a next knob.
  3. Virtual calls / deep inheritance for order kinds — use enum class + switch.
  4. Exceptions for normal rejects — return Rejected events; exceptions for truly exceptional I/O only.
  5. Logging in the inner loop at Info level — gate or keep out of match.

Types that read well in review

enum class Side : uint8_t { Buy, Sell };
enum class OrderType : uint8_t { Limit, Market };
enum class EventType : uint8_t { Accepted, Rejected, Trade, Cancelled };

struct OrderRequest {
  uint64_t order_id;
  Side side;
  OrderType type;
  int64_t price;  // ticks; ignored for Market
  int64_t qty;
};

Prefer strong enums over bool is_buy and stringly-typed APIs.

Clocks

Clock Use
steady_clock Latency histograms around submit
system_clock Human log timestamps only
Sequence integer Matching causality / FIFO debug

Never use wall time for priority.

v1 ships without a separate logger or scope-timer header — CLI prints event lines only.

API surface (const correctness)

class MatchingEngine {
public:
  std::vector<Event> submit(const OrderRequest&);
  std::vector<Event> cancel(uint64_t order_id);
  std::vector<BookLevel> bids(std::size_t depth) const;
  std::vector<BookLevel> asks(std::size_t depth) const;
  // optional:
  std::optional<BookLevel> best_bid() const;
  std::optional<BookLevel> best_ask() const;
};

All mutation through submit / cancel. Snapshots are const.

Header vs TU split

For a one-day project: headers for types + book + engine, thin main.cpp and test_*.cpp is fine.

Split .cpp only if compile times hurt or you want clearer linker boundaries. Avoid header-only chaos with heavy STL in many TUs if you later grow — not a day-1 problem.

Build

  • CMake ≥ 3.16-ish: two targets matcher, lob_tests.
  • -Wall -Wextra -Wpedantic; Debug + Release configs.
  • Sanitizers as optional local habit: -fsanitize=address,undefined in Debug (document in README; don’t require CI day one).

Latency measurement (secondary polish)

If ahead of schedule:

For i in 1..N:
  t0 = steady_clock::now()
  engine.submit(...)
  record(now - t0)
Report p50 / p95 / p99 in ns or µs

Caveats to say aloud: microbench without CPU pinning, warm-up, or fixed scenario is indicative only. Still shows engineering taste.

What “HFT matching” adds (vocabulary)

  • Core affinity, kernel bypass networking (not matching itself)
  • Custom allocators / arena for orders
  • Contiguous price levels, cached BBO pointers
  • Avoiding shared atomics on the book; shard by symbol
  • Deterministic replay from journal for incident response

Your project stops at correct single-threaded CLOB — then talks about the ladder above.

Anti-patterns to avoid in this repo

  • Singleton Exchange::instance()
  • new Order polymorphism tree
  • Mixing sockets into v1
  • Premature template metaprogramming for Side
  • Assert-only “tests” with no golden scenarios
