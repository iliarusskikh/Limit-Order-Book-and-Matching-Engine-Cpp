Normative rules

06 — Events, Fills & Invariants

Event-sourced thinking (light)

Treat the engine as: input message → state transition → event list.

Callers (CLI, tests, future gateway) should not peek private book guts; they consume events + snapshots.

Event types (v1)

Event When Key fields
Accepted New order passed validation (and may immediately trade) order_id, side, type, qty, price
Rejected Validation / cancel miss / duplicate order_id (if any), reason
Trade Fill between maker & taker maker_id, taker_id, price, qty
Cancelled User cancel or market residual cancel order_id, residual_qty, reason
BookSnapshot Optional explicit; or CLI-only via API levels

Ordering recommendation for one submit:
Accepted (if new) → zero or more Trade → optional residual Cancelled (market) → (rest is silent except later snapshots).

Rejects: single Rejected, no trades.

Some designs emit Accepted only if rested; others always on validation pass. Lock one: recommend Accepted on validation pass before matching, so partial take+rest still has one accept + trades. Document it.

Trade event semantics

Trade {
  maker_id,   // resting
  taker_id,   // aggressor
  price,      // maker's price
  qty         // > 0
}

Multiple trades per submit are normal (walk book / multi-order level).

Reject reasons (enum)

Keep a small closed set:

  • DuplicateId
  • InvalidQty
  • UnknownOrderId (cancel)
  • EmptyBook (optional — usually not a reject for market; just cancel residual)

Invariants (strong)

Define live = orders with remaining qty in the book.

  1. Uncrossed: bids.empty() || asks.empty() || best_bid() < best_ask()
  2. Positive live qty: every live order has qty > 0
  3. Index bijection: id in index ↔︎ exactly one book node
  4. Aggregates: level total = sum of remainings
  5. No resting markets
  6. Conservation on submit(qty Q):
    Q = sum(trade.qty) + rested_qty + cancelled_residual_qty

Debug builds can assert 1–5 after each op. Tests assert 6 on scenarios.

Qty accounting examples

Exact fill

NEW sell 10@100 against bid 10@100 → one trade 10; rested 0; cancelled 0.

Partial + rest

NEW sell 4@100 against bid 10@100 → trade 4; bid rests 6; sell fully filled.

Market vs thin

Asks total 30; MARKET buy 100 → trades sum 30; cancelled residual 70; rested 0.

Snapshot vs event stream

  • Events narrate what happened.
  • Snapshots narrate what remains.

Golden tests: either diff event logs, or interleave CHECK_* directives in scenario files. Both are valid; CHECK directives fail fast with clear messages.

Determinism

Same scenario file → same events (ids, prices, qtys, order of trades).

Avoid:

  • iterating unordered_map for output ordering of trades (trades should follow match order, not hash order)
  • timestamps in golden compare strings (print seq numbers; keep clocks out of asserts)

Failure modes that look like “random bugs”

Symptom Likely cause
Crossed book after submit Rested before matching / wrong marketability test
Wrong FIFO push_front by mistake / sort by id
Cancel fails intermittently Stale index after fill
Aggregate ≠ sum Forgot to update on partial
Double trade Didn’t erase empty level; matched ghost
