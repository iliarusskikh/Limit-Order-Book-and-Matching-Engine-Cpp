03 — The Limit Order Book

Book as a sorted catalogue of intent

A limit order book (LOB) stores resting orders:

  • Bids: buy limits, sorted descending by price (best = highest).
  • Asks: sell limits, sorted ascending by price (best = lowest).

Within one price level, orders form a queue (arrival order for price-time priority).

        BIDS (desc)              ASKS (asc)
   price  qty  (FIFO queue)   price  qty  (FIFO queue)
   100 ←─ 30  [A, B]          101 ←─ 20  [C]
    99 ←─ 50  [D]             102 ←─ 40  [E, F]
    98 ←─ 10  [G]             103 ←─ 15  [H]

   best bid = 100             best ask = 101
   spread = 1 tick

L1 / L2 / L3 depth

Level Contents Typical use
L1 Best bid/ask price + size (sometimes just BBO) Quotes, simple UIs
L2 Top N levels: price → aggregated size (± order count) Depth views, impact estimates
L3 Every order id at every price (full book) Reconstruction, surveillance

Our API exposes L2 snapshots (bids(depth), asks(depth)). Internally we store enough for L3 (individual orders) because matching needs FIFO queues.

Resting vs aggressing

  • Resting (passive): on the book, waiting.
  • Aggressing (active / taking): incoming order that matches immediately.

An incoming limit can be both: take some liquidity, then rest the remainder (partial take + book). That path is mandatory golden-test material.

Price levels vs orders

Two layers:

  1. Price level: key = price; value = aggregate metadata + queue of orders.
  2. Order: id, remaining qty, side, …

Operations:

Op Level effect Queue effect
New rest Create level if needed; add qty Push back
Trade vs head Decrease aggregate Decrease head qty or pop
Cancel middle Decrease aggregate; drop empty level Erase that node
Level empty Erase price key —

Aggregation for snapshots

For L2 level at price p:

total_qty(p)    = sum of remaining_qty over orders at price p
order_count(p)  = number of orders at price p

Snapshot of depth N: first N keys in bid/ask sort order.

Empty book → empty vectors; one-sided book is normal.

Crossing and why matching must drain it

If someone submits a buy limit at 105 while best ask is 101, the book would cross if you rested blindly. Correct engine:

  1. Match 105-buy against asks at 101, 102, … while ask_price ≤ 105 and qty remains.
  2. Only then rest residual on the bid at 105 (if any).
  3. Post-condition: not crossed.

Rule of thumb: never insert a resting order that would cross; matching first is mandatory.

Book of one instrument

v1: one OrderBook inside one MatchingEngine.

Multi-symbol production sketch:

// gateway routes by symbol; each book single-threaded or shard-owned

Sharding and concurrency are ops/architecture, not day-1 matching logic.

Display vs matchable liquidity

On real exchanges, displayed size may differ from matchable (icebergs, odd lots, retail segments). Our book: all resting qty is displayed and matchable.

State you must track beyond the two maps

Structure Purpose
id → (side, price, …) index O(log n) / O(1) cancel without scanning whole book
Monotonic seq (optional) Explicit FIFO tie-break if you don’t trust deque order alone
Event buffer Return trades/acks from submit

Cancel without an id index forces linear scan — unacceptable even in a teaching engine once N grows. Plan includes an order index.
