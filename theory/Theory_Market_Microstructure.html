01 — Market Microstructure Essentials

What problem does a matching engine solve?

A market needs a mechanism that turns intent (“I want to buy 100 @ 101”) into trades when two parties’ intents are compatible, and otherwise queues intent where others can see it (liquidity).

Two classical designs:

Design How price is found Book role
Call / batch auction Periodic clearing price Orders accumulate; match at discrete times
Continuous limit order book (CLOB) Continuous bilateral matching Resting orders form a live price schedule

This project implements a single-instrument continuous CLOB — the workhorse of equities, futures, and most crypto spot venues.

Agents and roles

  • Liquidity provider (maker): posts resting limit orders that sit on the book. Earns the spread when hit (in fee models: maker rebate). Provides depth.
  • Liquidity taker (aggressor): submits an order that immediately crosses the spread and trades. Pays the spread (taker fee on many venues).
  • Same participant can be maker on one order and taker on another.

Note: “Matching is not pricing theory — it is a deterministic state machine that allocates trades under published priority rules.”

The bid–ask spread

At any moment (both sides non-empty):

best bid  = max{ buy prices on book }
best ask  = min{ sell prices on book }
spread    = best ask − best bid

Invariant (continuous book after each message): if both sides have liquidity, best bid < best ask (or ≤ only if the venue allows locked markets — we forbid crossed and locked: require best_bid < best_ask).

  • Crossed book (bid ≥ ask): bug or incomplete match — never leave the book this way after an operation.
  • Locked book (bid == ask): some venues allow; many equity markets do not. Our v1: treat equality as invalid post-state (matching should have traded through).

Midprice (reference only; not used for trade pricing here):

mid = (best bid + best ask) / 2

Price discovery vs matching

  • Matching allocates quantity between orders under rules (priority, self-trade policy, TIF).
  • Price discovery is the economic process by which the book’s resting prices reflect information.

Your engine implements matching. It does not invent a “fair value.” Trade prices emerge from who rested at what price (maker convention — see note 04).

Depth and impact (intuition)

  • Top of book (L1): best bid/ask price and size — what a market order hits first.
  • Depth (L2): several price levels of aggregate size — what a large sweep walks through.
  • Market impact: large aggressive orders consume multiple levels → average fill price worsens vs mid. Your “walk the book” tests encode this mechanically.

For portfolio storytelling: show a scenario where a market buy of 100 against thin asks fills at several ascending prices — that is impact, demonstrated in code.

Continuous matching cycle (mental model)

For each inbound message (new / cancel / …):

  1. Validate (qty, id uniqueness, side/type consistency).
  2. Match if the order is marketable against the opposite side.
  3. Rest any remaining limit quantity on its side (market residual: policy-dependent — we cancel).
  4. Emit events (accept, trades, cancel residual, reject).
  5. Assert invariants (no crossed book; qty accounting).

This is exactly MatchingEngine::submit / cancel in the plan.

Tick size and lot size

Real venues constrain:

  • Tick size: minimum price increment (e.g. $0.01).
  • Lot size: minimum quantity increment (e.g. 1 share, or 100).

Representation choice for systems work:

  • Store price as integer ticks, qty as integer lots.
  • Never use double on the match path (rounding bugs, non-associativity, hard golden tests).

Example: tick = 0.01 → display price 100.25 ↔︎ integer 10025.

v1: document a tick label; optional validation that price % tick == 0 can wait if timeboxed.

Why portfolio projects implement CLOBs

These notes emphasize:

  1. Can you encode rules as invariants + tests?
  2. Do you choose boring correct structures first?
  3. Do you know what “price-time priority” means under partial fills?
  4. Can you explain maker/taker and trade price without hand-waving?

Your MDS companion shows I/O; this project shows market rules + C++ judgment.

What we deliberately omit (and the real-world name)

Omitted Real-world concept
Multiple symbols Matching engine sharded by instrument
Networking Order gateway / OUCH / FIX / binary OE
Fees Fee schedule alters effective priority sometimes
Auctions Opening/closing cross, halt re-open
Hidden liquidity Reserve / iceberg / dark
Pro-rata matching Futures allocations (e.g. some CME products)
Self-trade prevention STP modes (cancel newest, cancel oldest, …)

Know the names; do not implement them in v1.
