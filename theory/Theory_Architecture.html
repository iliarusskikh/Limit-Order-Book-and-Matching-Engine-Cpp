Data structures inside OrderBook

bids_:  map<price, Level, greater<price>>   // begin() = best bid (highest)
asks_:  map<price, Level>                   // begin() = best ask (lowest)

Level {
  total_qty          // sum of remaining qty at this price (kept incremental)
  deque<Order>       // FIFO: front = oldest = next to match
}

by_id_: unordered_map<order_id, BookLocation{side, price}>
        // O(1) locate for cancel; then scan deque at that level

Why two containers: map answers “which prices exist, in price order?”; deque answers “who arrived first at this price?” See also Theory_Data_Structures.

MatchingEngine ↔ OrderBook

  • submit never mutates the book except through OrderBook methods.
  • Match path: peek best_ask_price / best_bid_price → take_best_ask / take_best_bid → emit TradeEvent.
  • Residual limit → OrderBook::add.
  • Residual market → CancelledEvent(RESIDUAL); no rest.
  • cancel → OrderBook::remove → CancelledEvent(USER) or reject.
submit(OrderRequest)
  │
  ├─ reject InvalidQty / DuplicateId  → stop
  ├─ emit Accepted
  ├─ while marketable: take_best_* → emit Trade
  └─ if remaining:
        Limit  → book.add(resting)
        Market → emit Cancelled(RESIDUAL)

Event types (types.hpp)

Event is a std::variant of:

  • AcceptedEvent — order passed validation (before matching)
  • TradeEvent — maker_id, taker_id, maker price, qty
  • CancelledEvent — USER cancel or MARKET residual
  • RejectedEvent — validation / unknown cancel id

Order for a successful NEW: ACCEPT → TRADE* → optional CANCEL(RESIDUAL).

L2 snapshot path

bids(depth) / asks(depth) walk the maps and return up to depth BookLevel rows (price, total_qty, order_count). Used by SNAPSHOT in the DSL and by golden checks.

Invariants enforced here

  • After ops with both sides live: best_bid < best_ask (is_uncrossed)
  • No resting market orders
  • Id index ↔ book nodes stay in sync on add / take / remove
  • Level total_qty tracks deque remainings
