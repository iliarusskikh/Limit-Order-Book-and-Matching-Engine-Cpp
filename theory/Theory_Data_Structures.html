05 — Data Structures & Complexity

Design goal for v1

Correct and obvious — not nanosecond optimal.

Default choice (locked for this project):

bids: map<price, deque<Order>, greater<price>>   // best bid = begin()
asks: map<price, deque<Order>>                   // best ask = begin()
index: unordered_map<order_id, OrderRef>         // cancel / locate

OrderRef can store side + price (re-find deque) or iterators (faster, more fragile on invalidation — prefer side+price+careful erase for v1).

Why std::map for prices?

Pros Cons
Sorted; begin() is best price O(log L) per level touch; node allocs
Exact semantics; easy erase of empty levels Cache-unfriendly
Clear teaching/review story Not HFT-grade

L = number of distinct prices with liquidity (often small vs number of orders).

Why std::deque for FIFO?

Pros Cons
O(1) push_back / pop_front Middle cancel is O(k) in deque
Stable enough for teaching Contiguous chunks; iterator invalidation rules

Cancel-in-middle: linear scan in the level’s deque is OK for v1 if levels aren’t huge; document it. Intrusive doubly-linked list per level fixes O(1) cancel — classic upgrade path.

Complexity cheat sheet (v1)

Let L = price levels on a side, k = orders at a level, T = trades emitted by one submit, D = snapshot depth.

Operation Typical cost
Rest new limit at price O(log L) map + O(1) push
Cancel by id O(1) index + O(k) find in deque + O(log L) erase level if empty
Match one level fully O(k) pops
Aggressive submit O(T + log L per level touched)
L2 snapshot depth D O(D) walking map iterators

Emphasize: correctness first; cite these bounds in README.

Alternatives (know, don’t build yet)

1. Flat array / price-indexed buckets

Map tick → level via index = price - min_price. O(1) best if you track best pointers. Needs bounded price range; re-centering on moves. Used in latency-sensitive books.

2. Intrusive lists + level pool

Orders are nodes; levels pooled; custom allocators. Excellent cancel and cache control. More code, more bugs — post-v1.

3. std::multiset of orders with comparator (price, time)

One container per side. Simpler mentally, weaker “level aggregate” updates, awkward L2 aggregation. Usually worse than map+queue.

4. Skip lists / btree

Production adjacent; unnecessary for portfolio v1.

Memory & allocation awareness

Each map node and deque block heap-allocates. For a portfolio engine:

  • Optional later: count allocations with a custom operator new — not in v1.
  • Do not introduce a custom pool until the book is correct.

review: “I’d preallocate order nodes and recycle them; hot path should avoid unordered_map rehash and map thrash under cancel storms.”

Index design detail

struct BookLocation {
  Side side;
  int64_t price;
  // optional: generation / seq to detect stale refs
};

unordered_map<uint64_t, BookLocation> by_id;

On fully fill or cancel: erase from by_id.
On partial fill: location unchanged (same price level).

Never store raw deque::iterator across operations unless you are meticulous about invalidation — easy footgun.

Snapshot implementation tip

vector<BookLevel> OrderBook::bids(size_t depth) const {
  vector<BookLevel> out;
  for (auto it = bids_.begin(); it != bids_.end() && out.size() < depth; ++it)
    out.push_back({it->first, sum_qty(it->second), it->second.size()});
  return out;
}

Keep sum_qty either maintained incrementally (better) or scanned (simpler, fine for small k). Incremental aggregates are the better v1 habit: update on insert/trade/cancel.

Concurrency (theory only)

Production patterns:

  • Single-threaded book per symbol shard; gateway pins symbol → thread.
  • Mutex per book (simple, limited).
  • Disruptor / SPSC queues into matching thread.
  • Lock-free books — research/expert territory; easy to get wrong.

v1: one thread, no locks. Say so in README — shows scope taste.

Thirty-second summary

“I used a map from price to a deque of orders for clear price-time semantics, plus a hash index for cancels. Best bid/ask are begin() on inverted/ascending maps. It’s O(log L) per level — fine for correctness. For latency I’d move to pooled levels, intrusive queues, and a contiguous price ladder with cached BBO.”

That paragraph is the portfolio win.
