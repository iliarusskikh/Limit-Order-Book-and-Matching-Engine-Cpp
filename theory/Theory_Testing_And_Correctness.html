08 — Testing & Correctness

Why golden tests beat “it printed something”

A matching engine is a pure-ish state machine. The portfolio bar is:

Same scripted inputs → bit-stable outputs (events + book checks).

That is how exchange QA and prop-shop desk tools think.

Test pyramid for this repo

Layer What Mandatory?
Unit-ish Insert/cancel/snapshot without full CLI Yes (Phase 1)
Golden scenarios G1–G9 File or embedded DSL Yes
Invariant asserts After each op in Debug / test hook Strongly recommended
Microbench submit latency Optional polish
Fuzz / random orders RNG sequences + invariant oracle Stretch / later

Scenario DSL

NEW <id> <BUY|SELL> <LIMIT|MARKET> <qty> <price>
CANCEL <id>
SNAPSHOT <depth>
CHECK_BEST_BID <price> <qty>
CHECK_BEST_ASK <price> <qty>
CHECK_TRADE_COUNT <n>
# optional richer checks as you grow:
# CHECK_LEVEL BID <price> <qty> <count>
# CHECK_NO_CROSS

Fail soft vs fail hard: test runner should abort scenario on first CHECK failure with line number.

Mandatory behaviours (map to G1–G9)

ID Tests the rule in note
G1 Rest when not marketable (04, 02)
G2 Exact fill + maker price
G3 Partial + residual rest
G4 Walk multiple levels
G5 FIFO same price
G6 Cancel + unknown reject
G7 Market residual cancel policy
G8 Uncrossed invariant
G9 Validation rejects leave book untouched

If time permits, add G4b: limit buy that sweeps two levels then rests residual between new BBO.

Property / invariant testing

Even without a fuzzer, after each command in the test harness:

assert(!crossed(book));
assert(aggregates_consistent(book));
assert(index_consistent(book));

This catches bugs golden scripts miss.

Deterministic output format

Lock an event serialization for diffs, e.g.:

ACCEPT id=1 side=BUY type=LIMIT qty=10 price=100
TRADE maker=2 taker=1 price=101 qty=4
CANCEL id=1 qty=0 reason=USER
REJECT id=9 reason=UnknownOrderId

Stable field order; no timestamps in compared lines.

Oracles

Two useful oracles:

  1. Hand-computed expected trades for small scripts (primary).
  2. Conservation + uncrossed as automatic checks (secondary safety net).

A third later: slow reference engine (multiset of orders) vs fast engine — differential testing.

What not to test in v1

  • Throughput under multi-thread contention
  • Network partial reads
  • Persistence / crash recovery
  • Fee calculations

Harness choice

Zero deps: custom CHECK macros / main that returns non-zero — preferred for portfolio clarity.

Catch2/GoogleTest: fine if you already know them; not worth adding for one day unless you move faster with them.
